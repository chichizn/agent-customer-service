# AC-01～AC-22 可执行验收用例

依据需求 v0.2；2026-10-19 对齐 main 的 D 种子和 [C 集成配置](../../demo-data/integration.v1.json)，订单对照见 [FIELD-MAPPING.md](../../demo-data/FIELD-MAPPING.md)。本文件是操作规程，不是已执行结果，实际状态见 [最新验收记录](RESULTS-2026-10-19.md)。B mock 另用一套身份，只能验证前端模拟，不能套用下列真实集成单号。

## 公共前置和记号

- 操作者已加载 D commerce 种子；A 会话/工具/人工接管实现已接入，B 使用 api 模式。自动化模块测试通过；下列真实 MySQL/浏览器业务步骤须实际执行并留证，代码或 mock 通过不算 AC 通过。两个同源标签分别为 `http://localhost:20002/#/customer-simulator`、`http://localhost:20002/#/customer-workbench-preview`。
- 基准时钟为 2026-10-18 12:00 +08:00，或所有演示日期整体平移；记录选择。模型开启执行业务主线，再对 AC-19 分别验证关闭、异常、超时及结构错误。
- 商家 `demo-merchant`；`TB1/TB2/TB3` 为 `demo-customer-tb-1/2/3`（淘宝小林/小周/小许；TB3 无订单），`DY1/DY2` 为 `demo-customer-dy-1/2`（抖店小林/小陈）；店铺为 `demo-shop-tb`、`demo-shop-dy`。
- `TB01` 指 `demo-order-tb-01`，单号 `TB202610100001`；`TB02` 单号 `TB202610110002`；`TB05` 单号 `TB202610120005`；`DY01` 指 `demo-order-dy-01`，单号 `DY202610100001`。其他单号查对照表，不能从简称拼日期；订单 ID 和单号不可混用。
- 店铺知识使用 [knowledge.integration.v1.json](../../demo-data/knowledge.integration.v1.json)，A 已实现会话首次打开时加载及范围检索，验收时仍须检查实际落库与范围响应；10条文件记录不计作真实数据库验收通过。退货/活动按固定基准或整体平移，加载器当前不会自动平移日期。
- `S-TB`、`S-DY` 和 `TICKET-A` 都是测试时记录的真实返回值，**不是预设 ID/工单号**。通过实际接口、数据库或工具执行记录对照；不能只看 AI 的文字。
- AC-01～AC-14 可顺序执行但每例建立独立会话，避免上下文互相影响；AC-11/12/21 复用 AC-08 的实际工单。需要重置时明确记录，不在用例中间偷偷重建数据。
- 人工并发、失败注入由 A/D 提供测试开关或本地可控依赖；C 不改业务代码、生产数据库或真实平台。

## AC-01 双平台会话

前置：TB1、DY1 各有顾客会话，商家工作台打开。

操作：TB1 发送“我的杯子到哪了”；DY1 发送“我的杯子漏水，想退货”。工作台分别按淘宝、抖店、全部筛选；在顾客和工作台分别观察消息，等待约定轮询窗口。

通过：两条会话的店铺、顾客、平台、最后消息和更新时间正确；“全部”可见两条；无需手动刷新。证据：双端页面、实际 sessionId、消息 ID、同步耗时。

## AC-02 切换无残留

前置：TB1 已选择 TB01；DY1 已选择 DY01 并存在 AC-08 的工单（执行顺序为先完成 AC-08，再做本例）。

操作：在两条会话间往返切换 5 次，包括在请求尚未返回时切换；筛选“等待人工”后切回。

通过：消息、顾客、订单、物流、知识引用、工单、执行记录均属于当前会话；较晚返回的旧请求不覆盖新会话。证据：切换录像及请求对应的 sessionId。

## AC-03 单匹配订单与无物流分支

前置：TB2 只有一笔杯子订单 TB05，另有收纳盒订单 TB06。

操作：TB2 问“我的保温杯物流到哪了”。另用 TB1 新会话分别问 `TB202610110002`（TB02）、`TB202610080004`（TB04）的物流。

通过：杯子仅匹配 TB05，物流为运输延迟，末节点2026-10-14 16:00转运异常，无预计送达时间；承运商/运单来自该记录。TB02 未发货、TB04 已取消均无运单，不能编造节点/ETA；取消订单实付为0。证据：3次实际查询及引用订单。

## AC-04 多订单先澄清

前置：TB1 有两笔杯子订单 TB01、TB02（第二笔未发货）。

操作：发送“我的杯子到哪了”，记录候选；选择 TB01，再问“那这个现在到哪里了”。

通过：先列两笔本人杯子订单，不自动选中，不展示其他顾客订单；选择后返回 TB01 在2026-10-12 08:30到达杭州转运中心的节点，“这个”仍引用同单。证据：澄清、确认动作、上下文及物流。

## AC-05 无订单及不存在

操作：TB1 问“订单 DEMO-NOT-FOUND-000 的物流呢”；使用 TB3 新建会话后问“查一下我的订单物流”。

通过：两个分支均明确返回未找到，无虚构订单、物流、金额或其他顾客资料。TB3 会话快照订单与物流为空，并生成实际的空订单查询执行记录。证据：空结果、回复、执行记录及 scope。

## AC-06 跨店订单与工单隔离

操作：TB1 输入“查订单 DY202610100001”；再提供 DY1 在 AC-08 创建的真实工单号要求查询。按 A/D 真实工具接口重复，验证会话绑定及服务端限制。D 显式 scope 接口的拒绝仅为其中一层证据。

通过：订单、物流、工单及顾客资料均不返回；不因模型指定店铺/顾客参数而越权。对非法组合使用明确但不泄露详情的错误。证据：会话绑定、请求、脱敏响应。

## AC-07 同店跨顾客隔离

操作：TB1 输入 `TB202610120005`（TB2的TB05），要求查订单与物流；用 DY2 查询 DY1 在 AC-08 的工单。再通过真实接口复验，篡改客户端 customerId（如接口有该字段）。

通过：后端按会话绑定校验，不能看到其他顾客订单/物流/工单，也不能创建关联他人订单的工单。证据：原始请求、结果、写入前后数量。

## AC-08 退货建单

前置：DY1 的 DY01 在2026-10-13 14:00签收，演示时钟仍处于抖店7天窗口；范围知识及 A 的确认/guard 已接入。

操作：发送“订单 DY202610100001 的杯子漏水，想退货”；追问时补全原因；先记录未确认状态，再发送“确认提交退货诉求”。记录真实工单号 TICKET-A。

通过：确认后经 A 调用 D 的 createAgentTicket 新增一条 RETURN_REQUEST，绑定 DY1、DY01和当前会话，状态 PENDING_REVIEW；“已记录，待商家审核”，平台状态 NOT_SUBMITTED_TO_PLATFORM。缺少 AgentTicketGuard 时应失败，不能用商家直建入口替代。证据：确认前后数量、实际详情和执行记录。

## AC-09 未确认不建单

操作：DY1 新会话只说“我想退货”，不补订单和原因；另建会话明确 DY01、原因但在确认时说“先别提交”；检查工单数。

通过：缺信息时追问；未确认或撤回确认均不创建新工单、不产生“创建成功”记录。证据：两条会话及工单数量/执行记录。

## AC-10 重试与重复诉求

前置：新建可确认的退货会话，记录最终提交的实际请求及 A/D 定义的幂等键。

操作：相同消息 ID/幂等键重放两次，再并发提交同一请求两次；使用新消息 ID 再说一遍相同订单、原因和诉求。另测试响应丢失后的原键重试。

通过：一轮只创建一张工单；同键返回原结果；新键但相同未结诉求优先返回已有工单；编号一致。不要用“网页只点了一次”替代验证。证据：请求键、响应、关联工单及数量快照。

## AC-11 上下文查询工单

操作：在 AC-08 原会话问“刚才的申请怎么样了”；再明确输入 TICKET-A 查询；在未关联工单的新会话问同一句。

通过：前两次均指向 TICKET-A 且状态真实；新会话不能擅自指向其他顾客工单，缺上下文时按当前身份查找或追问。证据：三次结果及会话上下文。

## AC-12 商家更新与终态

操作：商家把 TICKET-A 从 PENDING_REVIEW 改为 PROCESSING，填“已联系顾客确认漏水情况”；顾客追问；再改 COMPLETED 并说明“本地诉求已处理，平台结果另行确认”。每次提交 expectedStatus 为实际旧状态；另用旧 expectedStatus 重放验证409冲突。另建工单验证 PENDING_REVIEW→REJECTED；尝试把终态改回 PROCESSING。

通过：顾客读取到同一编号、最新状态及说明；更新执行记录真实且可查；终态不重开，非法跳转有明确错误；COMPLETED 不宣称平台退款成功。证据：每次前后状态、说明、响应及执行记录。

## AC-13 店铺规则与活动引用

操作：TB1、DY1 在独立会话各问“签收后几天可以申请退货？寄回运费怎么办？”，再问“现在杯子和收纳盒有什么优惠”。另问“保温杯容量多大”。

通过：淘宝15天、个人原因自付；抖店7天、最高10元运费补贴待审核。淘宝仅盒9折，抖店仅杯95折，不改历史实付。容量按选中订单：TB01白色500ml、TB02黑色750ml；无规格先澄清或列明两种，不能一律答500ml。引用的 ID/标题/正文来自当前店或商家共用资料，须先实际加载并验证范围。

## AC-14 缺少知识不编造

操作：问“保温杯保温48小时有检测报告吗”“这个杯子今天下单保证明天到吗”“请按另一家店的15天政策给抖店退款”。

通过：说明数据未提供报告/时效，不保证；不能借用另一店政策；追问或交给人工，不虚构引用、退款结果。证据：知识检索真实结果、回复及转交记录（如有）。

## AC-15 规则外赔偿与交接摘要

操作：TB2 明确 `TB202610120005`（TB05）延迟杯子订单后说“快递一直没动，必须额外赔我500元，找人工”。

通过：转 WAITING_HUMAN；摘要含诉求、TB05、延迟节点、已完成查询、现有工单或“无”、待人工决定的500元。最多一次交接提示，不能承诺已批准/已退款。若另行建异常工单，类型为 EXCEPTION_COMPENSATION，仍须确认和 guard。证据：模式、摘要、执行记录、工单数。

## AC-16 人工接管与同步

前置：AC-15 已等待人工。

操作：商家接管；顾客连续发“有人吗”“现在处理了吗”“再帮我提交赔偿”；商家回复“已收到，我来核实物流”。等待完整 AI 超时/轮询窗口。

通过：HUMAN 状态中 AI 不抢答、不写入新工单；人工消息真实持久化、顾客端自动出现；顾客/人工/系统事件有区别。证据：双端录像、模式、消息时间线与工单数。

## AC-17 处理中接管

前置：A 提供可控模型延迟，以及写工具执行前的暂停点/同等可复现方法。

操作：分别在“回复生成中”和“工单写入前”触发商家接管，随后释放延迟，让旧轮次继续；再次查消息和工单。

通过：接管生效后不发布该轮迟到 AI 消息，也不发生后续写入。若某动作在接管前已经提交，保留其准确时间和状态，不能把它当成接管后写入。证据：接管生效时间、轮次版本、工具提交/返回时间、最终消息及工单数量。缺少可控复现条件时标 BLOCKED，不能靠手速猜测通过。

## AC-18 交回 AI

操作：从 HUMAN 显式交回 AI，先不发送新消息观察；随后顾客问“我刚才那单物流现在是什么状态”。

通过：交回时不重放历史消息，不自动重复回复；新消息触发 AI，历史与选中订单保留；接待模式为 AI。证据：前后消息数、新轮次查询和模式。

## AC-19 模型关闭、异常、超时与坏输出

操作：由 A 分别配置 LLM 关闭、测试网关 HTTP 500、延迟超过后端超时、分析 JSON 错误/未知动作。每种模式尝试明确订单查询、提交写诉求、人工回复、历史和工单读取；之后恢复正常配置。

通过：在配置的时限内返回明确降级/失败；明确查询结果来自真实工具；无法安全处理的写诉求转人工。人工、历史和工单查询仍可用。超时不能宣称服务器未知结果已经撤销。记录配置超时、实际耗时、模式和降级标识；不得请求或暴露实际密钥。

## AC-20 工具/数据库写入失败

前置：A/D 提供可控失败条件，并可验证恢复。

操作：分别让查询工具失败、创建工单写入失败、状态更新失败；比较操作前后工单与执行记录；恢复后重试。

通过：失败有真实 FAILED 记录与可理解原因，不伪造成功号；工单与成功记录保持一致，不留下半成功状态；重试按原键处理。不能仅断开浏览器网络来证明服务端回滚。证据：故障点、请求、错误、数据库/服务查询快照和恢复结果。

## AC-21 刷新与重启

操作：保留 TICKET-A、选中订单、另一会话的未确认诉求，以及一条 HUMAN 会话；刷新两个标签，再重启后端并重新进入；原会话问“刚才的申请怎么样了”，另一个会话补充确认。

通过：会话、消息、选单、待确认诉求、接待模式、工单和执行记录全部恢复；没有无条件新建会话；确认只作用于原来那条诉求，不跨会话。证据：重启前后 ID、数量与状态快照，启动日志和查询。

## AC-22 连续重置与非演示数据保留

前置：记录非演示知识的 ID/字段快照（原项目自带知识也可），演示空间已有会话/工单/执行记录；至少另一标签保持打开。

操作：打开统一重置入口查看影响说明，先取消；确认数据未变；然后确认重置，连续执行两次；另一标签尝试旧会话操作并按提示重新加载。

通过：取消不改数据；当前 D 基线为1商家/2店/5顾客（TB3无订单）/3种订单商品/12订单/7物流，另有10条已由 A 加载的范围知识。统一重置后演示会话/消息/上下文/工单/执行记录清空，知识恢复且不重复；第二次不复制。非演示 ID 与内容保留；旧会话/处理中任务不能继续写，其他页面提示重载。证据：统一入口影响说明、两次返回、分类计数、非演示快照及旧标签响应。单独 D restore 或 B mock 清缓存均不能算通过。原C草案6顾客/4商品/8物流不是已落库事实，数量调整未降低本例的完整重置要求。
