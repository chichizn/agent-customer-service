# 多平台电商客服数字员工 — 功能需求说明

> 版本：v0.2，供开发讨论和验收使用
>
> 更新日期：2026-10-18
>
> 技术基线：当前本地 Vue 3 + Java Spring Boot + MySQL 项目
>
> 交付目标：在现有项目上完成可操作、可重复演示的业务 Demo

## 1. 产品目标与第一版边界

面向同时经营多个电商店铺的小商家，提供统一客服工作台。客服数字员工能够理解顾客诉求、查询订单与物流、依据商品知识和店铺规则回答问题、创建及查询服务工单，并在需要时交给商家人工处理。

第一版需要证明：来自不同平台的咨询，可以进入同一个工作台，并在各自正确的店铺和顾客范围内完成业务处理。

### 1.1 本版采用的范围

| 项目 | 本版约定 |
|---|---|
| 基础项目 | 优先复用本地代码，保留 Vue 和 Java 技术栈 |
| 使用规模 | 1 个演示商家、2 家演示店铺 |
| 平台组合 | 暂定淘宝 + 抖店，沿用历史建议，作为本版设计假设 |
| 主要用户 | 商家/客服人员，以及顾客模拟入口中的预置顾客 |
| 交付形式 | 可启动 Demo、演示数据、启动及演示说明、备用操作视频 |
| 团队与开发约束 | 当前四人：1 位全栈、2 位熟练借助 AI 开发的成员、1 位支持成员；参考历史约两天开发窗口收敛范围，实际排期另行确认 |

### 1.2 模拟与实际运行的边界

| 内容 | 本版要求 |
|---|---|
| 平台消息 | 通过项目内的顾客模拟入口产生，页面标明模拟模式 |
| 店铺、顾客、订单、物流 | 使用项目预置数据，分别绑定淘宝或抖店 |
| 商品知识和店铺规则 | 可被真实查询和引用，规则明确标注为演示店铺规则 |
| 大模型 | 使用后端配置的模型 API 实际调用；关闭或失败时提供明确降级 |
| 工具执行 | 后端真实执行查询和写入，结果来自实际数据 |
| 服务工单 | 在本系统数据库内创建、查询和更新，返回可追踪的工单号 |
| 人工接管 | 实际改变会话接待模式，人工消息能够出现在顾客端 |
| 平台退款、退货申请 | 本版不执行真实平台操作，不声称资金退款或平台受理成功 |

本文是目标功能说明，不代表这些功能已经全部实现。历史记录中的 React、Go、PostgreSQL、渠道适配器及内存启动方案，不作为本地项目的能力依据。

| 能力 | 当前代码情况 | 本版处理 |

| LLM 对话 | 已有场景/意图/情绪分析及回复生成，携带最近 10 条历史消息 | 复用调用基础，补充可验证的工具执行流程 |
| 规则兜底 | LLM 未启用或调用异常时使用关键词与固定回复 | 保留，但业务结果必须来自工具实际执行 |
| 商品、活动、FAQ | 已有管理接口，参与对话关键词检索 | 增加店铺适用范围和引用展示 |

| 意图、提示词、规则配置 | 数据可管理，未被核心对话动态消费 | 保留现有页面，本版不要求完整动态规则引擎 |
| 会话上下文接口 | 更新接口仅记录日志，读取接口返回空对象 | 实现订单选择、待办诉求等必要业务上下文的持久化 |
| 订单、物流、服务工单 | 未见对应业务实体和完整处理链路 | 新增 |
| 工具执行与人工协作 | 当前主要是回复生成和卡片类型选择 | 新增实际工具执行、人工回复及接待状态管理 |
| 向量化、导入导出 | 部分接口返回模拟结果 | 不纳入本版验收，不作为已完成能力展示 |

本地启动信息以配置为准：前端当前配置端口为 `20002`，后端为 `10002`；前端 Node.js 要求为 `>=20.19.0`。后续启动文档需与实际配置一致。

## 3. 用户角色与核心场景

| 角色 | 主要操作 |
|---|---|
| 顾客（模拟） | 选择店铺和预置身份、发送咨询、确认订单和诉求、查询工单进度 |
| 商家/客服 | 查看两家店铺会话、查看业务资料、接管回复、更新本地工单状态、交回 AI |
| 客服数字员工 | 在授权范围内检索知识、调用工具、追问信息、受理诉求并交接人工 |

本版使用单商家演示环境，可复用现有游客入口。多商家账号体系、生产认证和坐席权限体系不属于本版；演示环境不能据此宣称已具备生产级权限隔离。

核心场景：

1. 淘宝顾客咨询物流：查找本人订单，多笔时确认具体订单，再返回真实预置的物流节点。
2. 抖店顾客申请售后：查询订单和店铺规则，补齐诉求并取得顾客确认，创建本地服务工单。
3. 顾客追问进度：找到先前创建的同一张工单，返回当前状态。
4. 顾客提出超出规则的要求：生成交接摘要，由商家接管并人工回复。

## 4. 功能需求

优先级定义：**P0 为演示交付必须完成，P1 为核心闭环稳定后再做，P2 为后续版本。** 以下 4.1～4.9 均属于 P0。

### 4.1 FR-01 双平台统一会话工作台

- 展示两个平台的会话列表，至少包含平台、店铺、顾客、最后一条消息、更新时间、接待模式。
- 支持按平台和接待模式筛选，支持切换会话及查看历史消息。
- 每条会话固定绑定商家、平台、店铺和顾客；切换会话时同步更新右侧业务资料。
- “等待人工”会话可通过筛选集中查看。
- 顾客消息、AI 回复、人工回复和系统事件有明确的视觉区别。
- 页面刷新后能够恢复已有会话；打开页面不能无条件创建重复会话。

**验收：**两个平台的消息可在同一工作台查看；切换会话不会残留上一会话的订单、工单或知识信息。

### 4.2 FR-02 顾客模拟入口

- 提供独立页面或入口，选择平台、店铺和预置顾客。
- 支持自由输入和快捷填入演示问题，支持查看 AI 与人工回复。
- 同一店铺、同一顾客可恢复已有演示会话，也可显式新建会话。
- 多笔订单时，可通过选项卡片或明确输入订单编号进行确认。
- 显示发送中、发送失败和重试状态，失败不能伪装为已完成。
- 工作台和顾客入口中的会话消息保持同步，无需依赖手动刷新页面。

**验收：**顾客入口发送的消息出现在对应商家会话中；商家人工回复可在顾客入口看到。

### 4.3 FR-03 商品知识与店铺规则问答

- 复用现有商品、活动和 FAQ，补充演示店铺服务规则。
- 店铺专属知识仅适用于对应店铺；明确标记为商家共用的知识可用于该商家的两家店铺。
- 回答区展示实际引用的知识名称、来源和相关内容，支持查看详情。
- 同名商品和相似问题也必须按当前店铺匹配，不能使用另一店铺的活动或政策。
- 知识不足时说明缺少依据，并追问或转人工，不编造价格、服务承诺或规则。
- 第一版允许使用现有关键词检索，不要求向量数据库。

**验收：**同一问题在不同店铺可根据各自规则返回不同答案；引用内容能在知识资料中找到。

### 4.4 FR-04 订单与物流查询

- 按当前会话的店铺和顾客查询订单，支持指定订单号和按商品描述查找。
- 展示订单号、平台、店铺、商品、数量、实付金额、订单状态和下单时间。
- 只有一笔明确匹配的订单时可继续处理；多笔匹配时先请顾客选择。
- 没有订单、订单不存在或不属于当前顾客时，返回明确提示，不暴露其他顾客或店铺数据。
- 查询物流时展示快递公司、运单号、当前物流状态和按时间排列的节点。
- 未发货订单提示尚无物流；节点未提供预计送达时间时，不编造送达承诺。
- 顾客确认的订单写入会话上下文，供后续“这个订单”“刚才那单”等表达使用。

**验收：**“我的杯子到哪了”可以完成查单、澄清及查物流；输入另一店铺订单号不会返回该订单资料。

### 4.5 FR-05 本地服务工单

- 首版至少支持退货诉求和异常/补偿诉求两类本地服务工单。
- 创建前需要明确订单、诉求类型和原因；AI 创建前需向顾客确认提交。
- 创建成功后返回真实工单号，关联会话、店铺、顾客和订单。
- 回复准确说明“已记录诉求，待商家审核”，工单状态与平台售后状态分别展示。
- 支持按工单号、当前订单或当前会话查询已有工单，解决“刚才的申请怎么样了”的追问。
- 商家可在工作台更新本地工单状态，并填写处理说明；顾客后续查询读取更新后的状态。
- 同一消息重试不能重复建单；同一顾客对同一订单重复提出相同且仍在处理的诉求时，优先返回已有工单。
- 写入失败时不生成成功文案、不展示不存在的工单号。

**验收：**创建 → 返回工单号 → 商家更新状态 → 顾客查询，同一工单的数据和编号始终一致；重复提交不会多出一张相同工单。

### 4.6 FR-06 人工接管与交回 AI

- 顾客明确要求人工、提出规则外补偿或出现无法处理的业务问题时，可转为等待人工。
- 商家可以主动接管任意演示会话。
- 交接摘要包括顾客诉求、关联订单、已完成动作、当前工单和待决定事项；缺失信息明确标注。
- 转人工时允许发送一次交接提示；进入等待人工或人工接待后，AI 停止自动回复和业务写操作。
- 人工消息持久化并同步到顾客入口，顾客继续发送的消息由商家处理。
- 商家可显式交回 AI，恢复后由新的顾客消息触发自动处理，避免重复回复历史消息。
- AI 正在生成回复时若发生接管，接管生效后不能再发送该轮迟到的 AI 回复或继续创建工单。

**验收：**接管后顾客连续发送消息也不会被 AI 抢答；交回 AI 后能够继续对话并保留历史。

### 4.7 FR-07 Agent 业务工具执行

第一版采用一个客服 Agent 配合有限工具，工具能力如下。名称用于对齐职责，最终接口由开发契约确定。

| 工具 | 输入含义 | 实际结果 |
|---|---|---|
| `search_knowledge` | 当前问题、可选商品 | 当前店铺可用知识及引用 |
| `get_order` | 订单号或商品线索 | 当前顾客的匹配订单或待确认列表 |
| `get_logistics` | 已确认订单 | 该订单物流或无物流原因 |
| `create_service_ticket` | 已确认订单、诉求、原因、确认信息 | 工单号、实际状态或失败原因 |
| `get_service_ticket` | 工单号或上下文线索 | 当前顾客的工单和处理记录 |
| `handoff_to_human` | 转交原因和已有处理信息 | 交接摘要及接待模式变化 |

- 模型可选择动作和组织回复；平台、店铺、顾客身份由后端从已校验的会话读取。
- 后端校验工具是否存在、参数是否完整、订单归属、当前接待模式及重复执行情况。
- 每轮设置明确的工具调用上限和超时；无法继续时追问或交接，不能无限循环。
- 回复中的订单状态、物流节点、工单号和执行成功与否，以工具返回为准。
- 模型不可用时可使用规则处理明确的查询，并标明降级；不能处理的写入诉求交给人工。
- 模型关闭、异常或输出格式错误均不得影响人工接待、历史查询和已有工单读取。

**验收：**更换问法仍可进入对应流程；工具失败、参数缺失或越界时，不会获得伪造的成功结果。

### 4.8 FR-08 业务执行记录

- 展示实际完成的动作，包括知识检索、订单查询、物流查询、工单创建、工单更新和人工交接。
- 每条记录包含动作名称、执行时间、成功/失败状态、结果摘要和相关业务编号。
- 记录与会话关联，刷新后可再次查看；失败记录包含可理解的原因。
- 业务记录应来自真实执行，现有固定“推理步骤”不能替代工具成功或失败记录。
- 展示可核对的结果摘要即可，不要求展示模型内部推理内容。

**验收：**每一条“工单创建成功”记录都能找到对应工单；失败动作不能显示为成功。

### 4.9 FR-09 状态保存与演示重置

- 会话、消息、已选订单、待确认诉求、接待模式、工单和业务执行记录保存在后端。
- 刷新浏览器或重启后端后，可以继续查看先前会话及工单。
- 提供演示重置入口，并在操作前说明影响范围、要求确认。
- 重置恢复该演示商家的初始店铺、顾客、商品知识、订单和物流，清除本轮演示会话、工单及执行记录。
- 重置范围仅限明确标记的演示数据，不清空其他已有项目数据；同一演示空间重置时提示其他打开页面重新加载。
- 重复执行重置不会复制初始数据或产生重复订单。

**验收：**刷新后“刚才的工单”仍可查询；重置完成后能从初始状态重新演示，原项目非演示数据保留。

## 6. 数据与状态约定

本节定义业务含义，不作为最终建表和接口契约。优先扩展现有 JPA 实体及 DTO，不要求替换数据库或引入新框架。

### 6.1 核心数据对象

| 对象 | 必要信息 |
|---|---|
| 演示商家 | 商家 ID、名称、演示数据标识 |
| 店铺 | 店铺 ID、商家 ID、平台、店铺名称 |
| 顾客 | 顾客 ID、所属店铺、平台侧标识、展示名称 |
| 会话 | 会话 ID、平台/店铺/顾客绑定、生命周期、接待模式、更新时间、必要业务上下文 |
| 消息 | 消息 ID、会话 ID、发送者类型、正文、时间、关联订单或工单 |
| 订单 | 订单 ID、店铺与顾客归属、商品明细、金额、状态、下单时间 |
| 物流 | 订单 ID、承运商、运单号、状态、物流节点 |
| 店铺规则/知识 | 知识 ID、适用商家/店铺、标题、正文、来源 |
| 服务工单 | 工单 ID/编号、关联会话与订单、顾客、类型、原因、状态、处理说明、创建及更新时间 |
| 执行记录 | 记录 ID、会话 ID、动作、执行状态、摘要、相关业务 ID、执行时间 |

平台、店铺、顾客、订单和工单等新增业务 ID 在接口中统一使用字符串。现有商品等数值主键可保留，通过契约明确转换方式，不做无必要的全库主键改造。

### 6.2 状态含义

| 对象 | 建议状态 | 规则 |
|---|---|---|
| 会话生命周期 | `active` / `closed` | 保留现有业务含义，与接待模式独立 |
| 接待模式 | `AI` / `WAITING_HUMAN` / `HUMAN` | AI 接待 → 等待人工 → 人工接待；商家可主动接管、显式交回 AI |
| 订单 | `PENDING_SHIPMENT` / `SHIPPED` / `DELIVERED` / `CANCELLED` | 预置演示状态，经适配映射为统一含义，不宣称等同平台官方枚举 |
| 本地工单 | `PENDING_REVIEW` / `PROCESSING` / `COMPLETED` / `REJECTED` | 待审核 → 处理中 → 已完成；待审核也可转为已拒绝，终态本版不重开 |
| 工具执行 | `SUCCESS` / `FAILED` | 仅记录实际执行结果，缺信息的追问不记为工具成功 |

会话接待模式、订单状态、本地工单状态分别管理。工单完成只表示本系统记录的处理完成，不能据此推断平台退款完成。

## 7. 演示数据

| 数据 | 最低准备量 |
|---|---|
| 商家与店铺 | 1 个商家、淘宝和抖店各 1 家店 |
| 顾客 | 每家店至少 2 位，覆盖同店不同顾客隔离 |
| 商品 | 3～5 种，包含杯子、收纳盒等易解释商品 |
| 订单 | 共 12 笔，每店 6 笔，覆盖未发货、运输中、已签收、已取消 |
| 多订单案例 | 至少 1 位顾客拥有多笔相似商品订单 |
| 店铺规则与知识 | 约 10 条，至少 1 组两家店规则不同的案例 |
| 物流 | 覆盖无物流、运输中、已签收和延迟案例 |
| 工单与人工案例 | 可在演示中创建工单，包含超规则补偿及人工更新状态案例 |

数据中保留同名商品、相似顾客标识或相似订单描述，验证系统根据会话归属查找，不会跨店混用。初始商品知识可共用，但店铺活动和售后规则必须能够区分。

## 8. 验收清单

| 编号 | 操作/条件 | 通过标准 |
|---|---|---|
| AC-01 | 两个平台分别发送消息 | 工作台可统一查看，平台、店铺和顾客标识正确 |
| AC-02 | 切换两条会话 | 消息、订单、工单和引用同步切换，无旧会话残留 |
| AC-03 | 单订单顾客查物流 | 查到该订单并展示实际物流节点 |
| AC-04 | 多订单顾客查物流 | 先澄清具体订单，不擅自选错订单 |
| AC-05 | 无订单或订单不存在 | 明确提示未找到，不编造订单 |
| AC-06 | 输入另一店铺订单号 | 不返回另一店铺订单及顾客资料 |
| AC-07 | 输入同店另一顾客订单号 | 不返回该订单及物流信息 |
| AC-08 | 顾客申请退货 | 明确订单及原因，确认后创建本地工单并返回编号 |
| AC-09 | 顾客尚未确认提交 | 不创建工单 |
| AC-10 | 同一消息重试、重复提出同一未结诉求 | 不重复建单，返回已有结果或工单 |
| AC-11 | 追问“刚才的申请怎么样了” | 找到同一工单并返回当前状态 |
| AC-12 | 商家更新工单状态 | 顾客再次查询看到更新结果和处理说明 |
| AC-13 | 两店询问同一售后规则 | 使用各自店铺规则并展示正确引用 |
| AC-14 | 知识不足 | 追问、说明缺少依据或转人工，不捏造承诺 |
| AC-15 | 顾客要求额外赔偿 500 元 | 不承诺赔偿成功，提供交接摘要并等待人工 |
| AC-16 | 人工接管后顾客继续发消息 | AI 不回复、不新增业务工单，人工消息可同步 |
| AC-17 | AI 处理过程中发生接管 | 接管后迟到的 AI 回复和后续写操作被阻止 |
| AC-18 | 商家交回 AI 后收到新消息 | AI 恢复处理，历史和上下文保留，不重复回复旧消息 |
| AC-19 | LLM 关闭、异常或超时 | 在明确超时内降级或提示失败，人工和查询功能仍可用 |
| AC-20 | 工具失败或工单写入失败 | 显示失败结果，不宣称创建成功，记录与实际一致 |
| AC-21 | 刷新页面或重启后端 | 原有会话、接待模式、已确认订单和工单可恢复 |
| AC-22 | 连续执行两次演示重置 | 恢复同一初始数据，不重复插入，不影响非演示数据 |

上述清单同时覆盖功能操作、数据归属、重复请求、人工并发和失败场景。验收以实际运行结果为准，固定欢迎语、静态卡片或写死的成功提示不算通过。

## 9. 稳定性与实现约束

- 沿用现有 Vue、Java、MySQL 主技术栈；Redis 不作为新增演示流程的必要依赖。
- 写操作需要后端校验并防止重复执行；工单创建和相关记录保持一致。
- 模型请求及工具执行均配置超时，页面不能无限加载；超时提示不得表示后台已取消未知结果的操作。
- 模型 API 密钥仅由后端读取，前端代码、日志和业务记录不展示密钥。
- 客户端只能选择预置演示身份，后端验证店铺与顾客组合，不能相信模型或任意请求参数指定的订单归属。
- 历史模型类型与后端字段存在差异，开发时以对齐后的实际接口契约为准，不直接依据已有 TypeScript 声明判断接口完成。
- 开发与演示环境使用本项目后端；生产配置中的外部 Mock 地址不作为本版业务数据来源。

## 10. 后续功能与本版不做的内容

### P1：闭环稳定后再安排

- 数字员工名称、服务店铺和自动接待开关的简易配置。
- 独立工单列表与更丰富的筛选。
- 有限场景的动态提示词、规则配置接入。
- 根据真实执行记录生成处理次数、成功率等基础统计。

### P2：后续产品化

- 取得授权后的淘宝、抖店真实消息、订单、物流和售后接口接入。
- 多商家租户、生产认证、坐席分配及权限体系。
- 真实售后审批、资金退款和平台状态同步。
- 向量检索、行业知识和解决方案的完整接入。
- 更多平台、复杂工作流和多 Agent 协作。

本版不安排跨平台消费者身份合并、语音客服、工作流拖拽编辑器或大型经营分析看板。未被实现并验证的能力不放入 Demo 的完成清单。

## 11. 建议实施顺序与分工

本节是开发建议，具体时间以团队确认后的排期为准。

| 阶段 | 完成标准 |
|---|---|
| 1. 本地基线 | 跑通 Vue、Java、MySQL，验证模型可用及规则降级，明确接口样例 |
| 2. 单店闭环 | 顾客输入 → 查单/澄清 → 读取规则 → 确认 → 创建工单 → 查询进度 |
| 3. 双平台工作台 | 两家店的数据接入统一页面，完成跨店和跨顾客校验 |
| 4. 人工协作 | 等待人工、接管、人工回复、交回 AI，验证处理中的接管 |
| 5. 演示稳定性 | 状态恢复、工具失败、重复提交、数据重置及完整验收 |

### 11.1 四人成员分工

保留历史中的 A、B、C 称呼，新增成员为 D。D 已确认能熟练借助 AI 完成开发。建议由 A 负责复杂编排与集成，D 负责边界明确的电商业务后端，B 负责 Vue 界面，C 负责数据与验证。

| 成员 | 主责 | 具体任务 | 独立交付物 |
|---|---|---|---|
| A：全栈成员 | Agent、会话与人工协作、总体集成 | 跑通项目；确定数据关系和接口契约；实现工具选择与结果回复；会话上下文；接管、人工回复和交回 AI；执行记录；统筹消息同步、重置和集成 | 能调用 D 的业务服务完成查单、建单、查询进度、转人工的完整后端链路 |
| B：熟练使用 AI 的成员 | Vue 前端 | 商家三栏工作台；会话筛选与切换；顾客模拟入口；订单/物流/工单卡片；知识引用与执行记录；接管与工单状态操作；双端消息展示与接口联调 | 可用固定 JSON 联调的完整页面，以及最终接通后端的操作界面 |
| C：支持成员 | 数据、验收与演示 | 按模板准备店铺/顾客/订单/物流/知识；执行 AC-01～AC-22；记录复现步骤；准备演示操作说明和备用视频 | 可加载的演示数据、验收记录、问题清单和操作视频 |
| D：新增的熟练使用 AI 的成员 | 电商业务后端 | 订单/物流/工单实体与服务；当前店铺和顾客范围查询；工单创建、去重、查询、状态更新；演示数据加载和业务数据恢复 | 可由接口直接验证、可供 A 调用的订单/物流/工单服务与明确返回结果 |

A 与 D 先共同确定店铺、顾客和订单关系、工单状态及接口样例，之后各自实现。D 的任务应拆成可以直接调用验证的业务接口，A 负责代码审查及集成，避免所有功能都等 A 完成后才能开始。

### 11.2 文件归属与协作边界

以下是建议的新增目录归属，开始实现时由 A 结合实际目录确认。表中尚不存在的目录属于开发建议，不代表已创建。

| 成员 | 主要负责位置 | 协作规则 |
|---|---|---|
| A | `backend/src/main/java/com/anjing/module/chat/` 及后端公共配置 | 负责会话相关实体、DTO、Agent 及接待状态；统一合并公共配置和公共 API 常量的变更 |
| B | `frontend/src/views/customer-service/`、`frontend/src/api/customer-service/` 及相关类型 | 统一负责前端页面、顾客入口、卡片、轮询刷新和调用封装；路由入口由 B 修改，接入前与 A 对齐 |
| C | `demo-data/`、`docs/acceptance/`、`docs/demo/` | 按 A/D 提供的字段模板准备数据；记录实际测试结果，不修改业务代码和公共配置 |
| D | 建议新增 `backend/src/main/java/com/anjing/module/commerce/` | 在独立业务模块提供订单、物流和工单能力；不直接修改 A 的 Agent 编排或会话接待模式 |

消息同步首版可由 B 轮询 A 提供的会话与消息接口实现，不要求引入 WebSocket。轮询失败、会话切换和页面离开时应正确处理，顾客端与工作台都需接入。

重置由 A 提供统一入口并控制演示范围：A 处理会话、消息、上下文及执行记录，D 提供订单、物流、工单和演示基础数据的恢复能力，C 验证非演示数据保留。D 不跨模块清空 A 的数据表。

后端执行记录使用 A 定义的统一记录方式；D 返回实际业务结果与业务编号。需要对写操作同步记录时，由 A/D 确定一致性处理，前端只展示已完成的结果。

### 11.3 第一阶段即可并行的任务

| 成员 | 最先做的任务 | 检查方式 |
|---|---|---|
| A | 跑通原项目，与 B/D 确认统一会话、业务对象和状态的 JSON 样例 | 原对话可用；业务对象有示例；接口职责明确 |
| B | 根据样例搭建工作台和顾客入口，先加载固定数据 | 能切换会话、展示业务卡片、触发接管与发送操作 |
| C | 根据模板准备两店数据和三个演示故事 | 每笔订单有正确归属，多订单、跨店规则差异等案例齐全 |
| D | 与 A 确认模型后，先实现订单和物流查询，再实现工单流程 | 不依赖大模型即可调用接口完成查单、查物流、建单和查进度 |

接口契约需要覆盖请求、返回、错误和状态，供 B 使用固定数据并行开发；订单、工单等查询与更新接口供 B 和 A 分别复用。接口变化先同步影响方，再合并调用方修改。

### 11.4 集成与验收责任

| 交付节点 | A / D 后端 | B 前端 | C 验收 |
|---|---|---|---|
| 单店闭环 | A 对话调用 D 工具，完成确认与工单创建/查询 | 顾客可发送消息，工作台能看到订单和工单 | 完成抖店售后故事，检查重复提交 |
| 双平台 | A 绑定会话身份，D 强制校验订单和工单归属 | 展示平台与店铺，切换会话同步业务资料 | 检查跨店、同店跨顾客和不同店铺规则 |
| 人工接管 | A 控制接待状态和处理中的 AI；D 写入按 A 定义的规则校验 | 顾客端与商家端可同步人工消息，可显式交回 AI | 检查 AI 不抢答、迟到回复不发出 |
| 演示冻结 | A 集成状态恢复和重置；D 完成业务数据恢复 | 完成异常提示和加载状态 | 跑完整验收表、重置复演、录制备用视频 |

每人使用独立分支并按可验证的小成果提交 PR，A 负责最终集成。优先沿业务闭环合并，建议每 2～3 小时检查一次已经完成的变更；避免到结束前才首次联调。A 的变更由 B/D 检查接口和代码，C 执行业务验收。

当进度不足时，先缩减配置页面、视觉动效和 P1 功能，保留查单、工单、人工接管和可重复演示的流程。最后至少 4 小时用于修复、验收和交付，不再扩大功能范围。

新增代码应落在当前 `frontend/src/` 和 `backend/src/main/java/com/anjing/` 体系内，不沿用历史讨论中的 Go/React 目录。

## 12. 完成交付标准

交付时应具备以下结果：

1. 本地项目可按说明启动，并能实际使用模型；关闭模型时可验证降级行为。
2. 淘宝查物流、抖店售后建单及查进度、商家接管三个演示片段能够连续操作。
3. AC-01～AC-22 均有实际验收结果，失败项不能标记为已完成。
4. 演示数据可重复恢复，刷新或重启不会丢失应保留的任务状态。
5. 提供启动说明、演示身份和操作路径、模拟范围与已知限制，以及备用演示视频。
6. 说明原项目来源和本次新增内容；仓库级授权范围需依据实际许可另行核实，本文不认定其商业使用授权。

功能实现、接口设计和验收均以本文件描述的本地项目范围为依据；范围调整后同步更新本文。
